# Подключение Debian LXC

Реализован агент для Debian 12/13 (amd64/arm64), systemd, kernel WireGuard
и отдельного сетевого пространства LXC в Proxmox. Root внутри контейнера
нужен для создания WireGuard-интерфейса и маршрута до мамы. Обычные
пользователи кабинета не получают ключи или административный доступ мамы.
Не используйте сеть хоста и не разделяйте namespace между контейнерами.
Каждому LXC требуется собственная запись машины и агент.

Это поддерживаемая конфигурация реализации, а не отчёт о проверке Debian:
в этой работе доступны только локальные проверки. Реальные Debian LXC,
изоляция двух машин и перезапуск контейнера ещё требуют стенда.

## Подготовка оператором

На Proxmox-хосте нужен загруженный модуль ядра WireGuard (`modprobe wireguard`)
и его загрузка после перезапуска хоста. Делает администратор Proxmox;
контейнер не должен получать управление модулями хоста. Предпочтителен
непривилегированный Debian LXC с отдельным namespace, systemd и
CAP_NET_ADMIN в собственном сетевом namespace. Агент не использует
userspace TUN, не требует проброса `/dev/net/tun` и не требует отключать
AppArmor целиком. Если политика конкретного хоста запрещает создание
WireGuard, оператор должен разрешить это в политике LXC. Установщик
проверяет создание временного kernel WireGuard-интерфейса и останавливается
при отказе; такая машина не отмечается подключённой.

Внутри LXC нужен исходящий HTTPS к кабинету (443/TCP), UDP к публичному
WireGuard endpoint мамы (обычно 51820/UDP), рабочие DNS, часы и доверенные CA.
Входящий публичный порт контейнера не требуется. На маме должны быть
настроены WireGuard и привилегированный сетевой helper; без него кабинет
возвращает 503 и сохраняет код для повторной попытки. Прикладной процесс
кабинета сам не получает CAP_NET_ADMIN.

Оператор собирает бинарник под архитектуру контейнера:

```
GOOS=linux GOARCH=amd64 go build -trimpath -o sreda-agent ./cmd/sreda-agent
```

Для arm64 заменить архитектуру на `arm64`. Передать в контейнер бинарник,
`deploy/agent/install.sh` и `deploy/agent/sreda-agent.service`, сохраняя их
в одном каталоге. Передавать по доверенному каналу и проверять контрольную
сумму полученного бинарника. Готового публичного сервиса скачивания пока нет.

## Установка пользователем внутри своего LXC

Под root:

```
apt-get update
apt-get install -y wireguard-tools iproute2 ca-certificates
./install.sh ./sreda-agent
```

В кабинете открыть `/machines`, добавить название машины и получить код.
Код действует 15 минут, показывается один раз и предназначен только агенту
этого контейнера. Это не приглашение человека и не пароль аккаунта.

```
sreda-agent enroll --origin https://cabinet.example.com
```

Код вводится скрыто по запросу, без аргумента командной строки и истории shell.
Затем:

```
systemctl start sreda-agent
systemctl status sreda-agent
journalctl -u sreda-agent --since '10 minutes ago'
```

Установщик уже включил автозапуск. Факт регистрации ещё не означает связь:
агент запускает WireGuard, открывает HTTP только на своём WG IPv4:9080,
затем отправляет контакт раз в 30 секунд. В кабинете «На связи» означает
недавний управляющий контакт (до 90 секунд), а не здоровье приложения.
Время последнего контакта сохраняется отдельно; отсутствие связи сохраняет
запись машины. Локальные приложения агент публикует по IP:порт loopback, например
`127.0.0.1:8080` или `[::1]:8080`, либо по IP, действительно назначенному
интерфейсу этой машины. Имена DNS, адреса WireGuard и соседних машин
агент не принимает.

## Протокол и чувствительные данные

Управление: HTTPS JSON `POST /api/agent/enroll` и
`POST /api/agent/heartbeat`. Регистрация передаёт одноразовый код, публичный
ключ X25519 WireGuard и отдельную случайную учётную запись агента. Сервер
хранит только хеши кода и этой учётной записи. Приватный ключ генерируется
на машине и не отправляется в кабинет. Код потребляется атомарно после
подтверждённого применения peer; конкурентное применение успешно один раз.

`/var/lib/sreda-agent` имеет режим 0700; `state.json` и `wg-sreda.conf` — 0600.
Состояние атомарно сохраняется до отправки регистрации. Если ответ потерян,
повторить ту же команду с тем же кодом: агент попробует восстановить ответ
по уже сохранённой учётной записи. Не удалять этот каталог при обновлении.
Незавершённое подключение не запускает службу; при окончательно истёкшем
непотреблённом коде оператор сохраняет закрытую резервную копию состояния,
создаёт новую запись или использует сценарий переподключения и повторяет
регистрацию. Обычные журналы и страницы машин не содержат секретов.

Отдельный токен шлюз→агент хранится в закрытой SQLite и состоянии агента,
передаётся внутри WG в `X-Sreda-Proxy-Token`. Заголовок
`X-Sreda-Publication` содержит только зарегистрированный ID публикации.
Агент не принимает адрес назначения из запроса и сохраняет исходный
Authorization приложения. Эти два внутренних заголовка удаляются перед
отправкой в приложение. Обновления карты маршрутов имеют монотонную версию;
удаление маршрута закрывает уже открытые upstream-соединения.

При отказе HTTPS агент повторяет контакт; после 90 секунд без подтверждения
закрывает локальные маршруты. При 401/403 прекращает службу и убирает свой
WG-интерфейс. Отзыв сетевого доступа на маме выполняется независимо от
доступности или добросовестности агента. Ошибка настройки/отзыва сети не
обозначается успешным подключением/отключением.

## Приёмка на отдельном стенде

Не выполнено локально: два Debian LXC, перезапуск LXC, управляющий HTTPS,
реальный WG handshake, доставка HTTP/WebSocket, попытки доступа между двумя
клиентами в обоих направлениях и ко всем административным портам мамы,
проверка отсутствия маршрутов после отключения/блокировки и после
перезапуска helper. Выполнять отрицательные сетевые пробы в обход агента
(самостоятельный WG-клиент), записывать результат в задачу 03. Одного
ограничения AllowedIPs в выдаваемом клиентском конфиге недостаточно.
