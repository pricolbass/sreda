# Сетевой helper и границы локальной проверки

Реализация 20 октября 2026 года; реальная Linux-сеть в этой работе не настраивалась.
На macOS проверяются HTTP-протокол ошибок и сборка для Linux. Это не проверка
применимости nftables, WireGuard или изоляции LXC.

Привилегированный `sreda-network` работает отдельной службой root с
`CAP_NET_ADMIN`. Кабинет обращается через Unix-сокет
`/run/sreda-network/control.sock`, доступный только root и группе
`sreda-network`. Пользователя `sreda` следует добавить в эту группу.
Создание группы, установка бинарника в `/opt/sreda/` и unit-файла выполняются
оператором. Файлы бинарников/units принадлежат root и недоступны для записи
пользователю кабинета. Кабинету не выдаются sudo или CAP_NET_ADMIN.

WireGuard-интерфейс `wg-sreda` с адресом `10.203.0.1/32`, приватным ключом
шлюза и публичным UDP endpoint заранее настраивает оператор через wg-quick.
Ключ не читается кабинетом. Автоматическое сохранение peers через SaveConfig
не включается: актуальное состояние клиентов хранится в БД Среды.
Подключения ограничены 100 записями: id 1–100 получают `10.203.0.(id+1)/32`.
Удалённые id не переиспользуются автоматически.

Helper принимает только ограниченный JSON с id, публичным ключом и точно
закреплённым /32; не принимает имя интерфейса, shell, путь, приватный ключ
или текст firewall от клиента. Системные программы запускаются без shell.
`apply` настраивает peer при закрытой клиенту политике, проверяет ключ и
AllowedIPs, затем разрешает обратный трафик. `remove` сначала убирает адрес
из разрешённого набора, затем удаляет peer и подтверждает его отсутствие.
Ненулевой результат, неизвестное состояние и таймаут дают HTTP 503, а не
подтверждение успеха. Повторная операция допускается.

В отдельной таблице `inet sreda`:

- запрещён весь forwarding с/на WireGuard, включая машины одного владельца;
- на вход разрешены только ответы на установленные шлюзом соединения от
  разрешённого /32; прочие обращения к маме через туннель запрещены;
- исходящий трафик шлюза разрешён только к разрешённым клиентским /32;
- IPv6 по туннелю не разрешён;
- правило запрета проверяется и для уже существующих соединений, без
  безусловного раннего `ct state established accept`.

Таблица устанавливается атомарно до открытия управляющего сокета. Глобальный
ruleset не очищается. При перезапуске helper набор клиентов пуст: сервер
должен повторно применить сохранённые разрешённые подключения; отсутствие
helper не обозначается как успешное подключение. Правила сохраняются при
его остановке. Операторская служба nftables не должна удалять таблицу Среды
после запуска helper. Запрещён flowtable offload для интерфейса Среды.

Настоящая приёмка требует Debian: проверить версию nftables, порядок units,
запреты для враждебного ручного клиента в обоих направлениях, IPv6, обращения
к административным портам мамы и перезапуск сетевых компонентов. Применение
peer не доказывает наличие WireGuard-handshake или исправность приложения.

Основание решений: [wg manual](https://git.zx2c4.com/wireguard-tools/about/src/man/wg.8),
[правила nftables](https://netfilter.org/projects/nftables/manpage.html),
[атомарная замена](https://wiki.nftables.org/wiki-nftables/index.php/Atomic_rule_replacement).
