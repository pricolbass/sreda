# Восстановление пароля

Локальная реализация задачи 11, 20 октября 2026 года.

Администратор открывает «Восстановление пароля пользователя», выбирает
обычного пользователя и создаёт ссылку. Ссылка показывается один раз и
действует 1 час; точный срок отображается в UTC. Администратор передаёт её
лично, без отправки почты. Создание следующей ссылки немедленно отменяет
предыдущую. Токен хранится только как SHA-256-хеш.

Пользователь сам задаёт пароль из 12–72 байт. Открытие страницы и ошибка
ввода не используют ссылку. Успешная смена пароля и использование ссылки
выполняются в одной транзакции; повторное или одновременное применение
не меняет пароль ещё раз. По просроченной ссылке смена не выполняется.

После успешной смены все сессии этого пользователя отзываются, а прежний
пароль больше не позволяет войти. Пароль не попадает в ответ администратору.
Ссылка содержит привязку к пользователю на сервере: подмена поля формы
не меняет целевой аккаунт. Смена пароля не изменяет роль, блокировку или
состояние ресурсов; заблокированному пользователю она не возвращает доступ.

## Аварийный пароль администратора

Публичной ссылки восстановления администратора нет. Оператор на маме
запускает локальную команду от имени системного пользователя `sreda`:

```sh
sudo -u sreda /usr/local/bin/sreda reset-admin \
  --data-dir /var/lib/sreda --login owner
```

Команда дважды запрашивает новый пароль в терминале со скрытым вводом.
Параметры каталога и логина нужно подставить из установленной конфигурации.
Она изменяет только пароль существующего администратора и отзывает все
его сессии. Обычный аккаунт, неизвестный логин и неподходящий пароль
отвергаются без создания или повышения прав аккаунта.

Для автоматизации доступен `--password-stdin`: одна строка из защищённого
stdin. Не передавайте пароль аргументом команды и не сохраняйте его в
истории терминала. Создание и оба способа восстановления используют
единую проверку длины и bcrypt-хеширование.

SQLite автоматически обновляется с версии 2 до 3 без пересоздания
пользователей и потери существующих записей. Конкурирующий вход также
перепроверяет актуальный хеш перед созданием сессии, чтобы проверенный
до смены старый пароль не создал новую сессию после её завершения.
