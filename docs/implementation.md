# Реализация первой версии

Язык Go выбран пользователем. 20 октября 2026 года пользователь поручил
реализацию спецификации и ограничил выполнение локальной средой. После
замечания о SOLID HTTP и прикладные правила выделены в отдельные модули.
Фактическое состояние требований отмечается в `.scratch/first-version/issues/`.

## Состав

`make build` создаёт три бинарника: `sreda` (CLI и кабинет), `sreda-agent`
(подключение и доставка к локальному приложению) и `sreda-network`
(привилегированный Linux helper). SQLite через `modernc.org/sqlite` работает
без CGO и отдельного процесса базы. Caddy завершает TLS и передаёт запросы
в Unix-сокет кабинета. systemd запускает процессы с разными правами.

Caddy использует постоянный wildcard-маршрут; добавление и отключение
публикации не перезагружает его конфигурацию и чужие WebSocket-соединения.
DNS API, выпуск сертификатов и модели ИИ в приложении не используются.

## Ответственность модулей

| Модуль | Ответственность | Внешний интерфейс |
| --- | --- | --- |
| `internal/identity` | Учётные записи, сессии, приглашения, восстановление | Операции Manager и типизированные результаты |
| `internal/machine` | Владение, одноразовое подключение, адреса, состояние подключения | Manager; сетевые операции через `tunnel.Gateway` |
| `internal/agentcontrol` | Получение карты и подтверждение её версии агентом | Controller; потребительский интерфейс `Routes` |
| `internal/publication` | Поддомены, права и желаемое/применённое состояние публикаций | Module; транспорт публикации через `Transport` |
| `internal/cabinet` | HTTP, CSRF/cookies, HTML/JSON, сборка модулей | Handler и совместимые CLI-точки входа |
| `internal/tunnel` | Ограниченный Unix-протокол helper и подтверждение Linux-настроек | Gateway и HTTP helper |

SQL и транзакционные операции находятся в закрытых SQLite-адаптерах.
Прикладные операции принимают решение по зафиксированному снимку; адаптер
применяет его атомарно. HTTP не распределяет адреса, не хеширует пароли и
не управляет переходами состояний. Общие данные протокола и проверка
синтаксиса цели находятся в `agentprotocol`, отдельно от runtime агента.

Это разделение соответствует причинам изменения кода: HTML/HTTP, правила
доступа, схема хранения и сетевой протокол меняются отдельно. Интерфейсы
введены у реальных сетевых способов подключения и между модулями; отдельная
иерархия и универсальный CRUD-репозиторий для каждого типа не нужны.
Подробности: [учётные записи](identity-module.md), [машины](machine-module.md),
[публикации](publications.md).

## Данные и согласование

В `sreda.sqlite3` сохраняются пользователи, bcrypt-хеши паролей (cost 12),
SHA-256-хеши случайных 256-битных сессий и одноразовых ссылок/кодов,
настройки кабинета, машины и публикации. Обычный пароль и исходный session
токен в базе не сохраняются. Сессия живёт 12 часов, проверяется на сервере,
отзывается выходом и сменой пароля. Новый вход атомарно проверяет, что
пароль не изменился, и заменяет старую сессию этого браузера.

SQLite использует WAL, foreign keys, busy timeout, IMMEDIATE write-транзакции
и одну связь на процесс. Миграции сохраняют пользователей и действующие
сессии из версии 1. Более новая неизвестная версия базы отвергается.

До применения WireGuard peer сохраняется привязанное намерение подключения.
Отмена запроса не отменяет независимую ограниченную компенсацию. При ошибке
очистки код, ключ и адрес остаются зарезервированными; очистка повторяется
после перезапуска. Незавершённое подключение не аутентифицирует агента.

Публикация имеет отдельные желаемое состояние, версию команды и версию карты
агента. «Настроена» означает применение нужной версии, а не здоровье
приложения. Отключение сначала сохраняет намерение и закрывает допуск,
затем завершает активные потоки. Неподтверждённое завершение остаётся ошибкой;
ожидание одного потока не удерживает общий замок других публикаций.

## HTTP и секреты

Кабинет доступен на одном сохранённом Host. Формы защищены случайной
CSRF-cookie `__Host-`, сравнением токена и точным Origin. Cookie — Secure,
HttpOnly, SameSite=Strict, Path=/, без Domain. Соседняя публикация не получает
cookie кабинета. Выход и изменения — POST. Кабинет задаёт CSP, запрет iframe
и no-store; политика кабинета не подменяет заголовки опубликованного приложения.

`X-Forwarded-Proto` принимается потому, что единственный вход сервера —
Unix-сокет с ограниченными правами, а Caddy перезаписывает заголовок. Запрос
без признака HTTPS отвергается, без HTTP-редиректа. Прокси очищает поддельные
Forwarded-заголовки и внутренние заголовки маршрутизации; Authorization
самого приложения сохраняется. Переменные окружения HTTP proxy не выбирают
маршрут к машине.

Приватный WireGuard-ключ агента создаётся и хранится на машине. Отдельный
секрет шлюз→агент нужен серверу для доставки, хранится в закрытой базе и
не возвращается в браузерные DTO или обычные журналы. Каталоги состояния
имеют режим 0700, файлы секретов — 0600. Создание администратора и его
аварийное восстановление доступны только через локальный CLI.

## Права и проверенные пределы

| Процесс | Права |
| --- | --- |
| `sreda` | Своя БД, Unix-сокет, сетевой доступ к опубликованным целям; без root/CAP_NET_ADMIN |
| `sreda-network` | Ограниченные команды WireGuard/nftables, закрытый управляющий Unix-сокет |
| `caddy` | TLS-ключ и доступ к сокету, без чтения базы кабинета |
| `sreda-agent` | CAP_NET_ADMIN/root внутри собственного сетевого пространства LXC |

Группа прокси даёт Caddy доступ к сокету; группа сетевого helper даёт кабинету
доступ только к его типизированному протоколу. Оператор владеет бинарниками,
unit-файлами, WireGuard конфигурацией шлюза, DNS и сертификатами.

Локальные проверки используют CLI/HTTP с настоящей SQLite, реальные
HTTP/HTTPS/WebSocket и Caddy с локальным CA. Linux kernel и сеть заменяются
только на внешнем сетевом интерфейсе тестового стенда. Это не подтверждает
реальную изоляцию LXC, публичный wildcard TLS или вместимость 100 машин.
До приглашения реальных пользователей нужна внешняя приёмка задачи 13;
ресурсные пределы проверяются задачей 14.


## Доступ пользователя

`internal/access` координирует отзыв аккаунта через интерфейсы identity,
publication и machine. HTTP не содержит SQL или последовательности сетевой
очистки. Блокировка и отзыв сессий атомарны; версия доступа владельца
проверяется повторно после дорогой проверки пароля и на каждом переходе
heartbeat. Долгие операции peer проверяют версию при завершении.

Желаемое состояние подключения (`desired_enabled`) хранится отдельно от
подтверждённого (`enabled`). Блокировка выключает оба и увеличивает версии
ресурсов. Включение после разблокировки — отдельные команды владельца для
машины и публикации. Подробности и границы проверки: [user-access.md](user-access.md).
