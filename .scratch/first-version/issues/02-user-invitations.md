# 02: Администратор приглашает пользователя

**What to build:** администратор создаёт в кабинете приглашение и лично передаёт ссылку человеку. Человек задаёт логин и пароль и получает собственный кабинет. Открытой регистрации и отправки почты нет.

**Blocked by:** 01 — Первый администратор входит в кабинет по HTTPS.

Status: resolved

- [x] Администратор может создать приглашение, получить ссылку, увидеть срок действия и отменить неиспользованное приглашение.
- [x] Срок действия и поведение незавершённой регистрации определены и отражены в интерфейсе.
- [x] Принятие действующего приглашения создаёт обычного пользователя с выбранными им логином и паролем. Коллизия логина обрабатывается без повреждения приглашения или чужого аккаунта.
- [x] Просроченная, отменённая и уже использованная ссылка отвергается. Одновременное принятие одной ссылки не создаёт несколько аккаунтов.
- [x] Пользователь может войти и выйти; ему недоступны административные операции, в том числе при прямом обращении к серверу.
- [x] Разделение пользователей проверяется на доступных к этому моменту данных и операциях; последующие задачи обязаны проверять владение своими новыми ресурсами.
- [x] Сценарий проверен с тестовыми аккаунтами. Приглашение реальных пользователей допускается после отдельной обязательной проверки закрытия доступа и изоляции в задаче 13.



## Comments

### 20 октября 2026 — реализовано и проверено локально

Кабинет администратора выдаёт одноразовые ссылки на 1 час, 24 часа или 7 дней.
В списке видны срок в UTC и состояние; неиспользованную ссылку можно отменить.
Открытая или незавершённая форма не расходует приглашение: оно используется
только в транзакции успешного создания пользователя. При коллизии логина
транзакция откатывается, и ссылка остаётся действительной. Исходный токен
показывается при создании один раз, в SQLite хранится только SHA-256-хеш.

Обычный пользователь входит по своему логину и видит собственный кабинет.
Административные запросы списка, создания и отмены проверяют роль на сервере.
На этом этапе персональные ресурсы ещё не добавлены; владение машинами
и публикациями обязаны проверять задачи 03–07.

Проверки через HTTP с настоящей SQLite: регистрация, вход/выход, отказ
в административных операциях, занятый логин с повторной попыткой, отменённая,
использованная и просроченная ссылки, незавершённая форма, одновременное
принятие одной ссылки двумя экземплярами приложения. Отдельный fixture
базы версии 1 проверяет обновление схемы с сохранением старой сессии и
возможностью создать обычного пользователя. Проверки данных выполняются
через HTTP; SQL используется только при подготовке старого/просроченного fixture.

TDD: первая HTTP-проверка приглашения падала с 404; после реализации прошла.
Проверка повторной отправки неверной формы использованной ссылки падала с 400;
после проверки действительности ссылки до обработки формы проходит с 410.

Все аккаунты и ссылки тестовые. Никакие приглашения людям не передавались.
Внешняя приёмка, блокировки и сетевая изоляция остаются за задачей 13.
Инструкция: [приглашения](../../../docs/invitations.md).

Проверки завершены: `go vet ./...`, полный `go test ./internal/cabinet`,
`go test -race ./internal/cabinet`, `go test -race ./internal/command`.
Процессный тест Unix-сокета повторён с разрешённым локальным сокетом после
отказа песочницы; прошёл. После добавления точного срока на странице принятия
повторно прошли обычный набор кабинета и соответствующий сценарий с race detector.
