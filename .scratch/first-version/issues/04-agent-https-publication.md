# 04: Пользователь публикует локальное приложение по HTTPS

**What to build:** пользователь выбирает подключённую машину, указывает адрес и порт своего приложения и свободный поддомен. Среда создаёт внешний HTTPS-адрес и доставляет запросы через маму и агент к указанному приложению, включая loopback, без ручной настройки мамы для каждой публикации.

**Blocked by:** 03 — Пользователь подключает Debian LXC через агент.

Status: resolved

- [ ] Работает полный путь интернет → Caddy на маме → WireGuard → агент в LXC → явно заданный адрес и порт приложения.
- [x] Произвольные тестовые веб-приложение и веб-API публикуются без интеграции с конкретным продуктом. Автоматический поиск приложений не требуется.
- [x] Два приложения одной машины публикуются через одно существующее подключение, без повторной установки агента или выдачи кода.
- [x] Поддомен проверяется и закрепляется за публикацией; конкурентный выбор одного имени не создаёт конфликтующих маршрутов. Собственные домены в этот сценарий не входят.
- [x] Пользователь может публиковать только на своей машине. Подмена идентификатора машины или публикации не даёт доступа к чужим ресурсам.
- [x] Агент принимает трафик только для зарегистрированных включённых публикаций своей машины и только к закреплённому адресу и порту. Неизвестная, чужая или неактивная публикация, соседний незарегистрированный порт и подмена цели отвергаются.
- [x] В кабинете видны «Настраивается», «Настроена» и «Ошибка» с причиной. «Настроена» появляется после подтверждения применения настроек и не означает проверку здоровья приложения.
- [x] Частичная ошибка настройки не выдаётся за успешную публикацию и не повреждает другие публикации; повторная попытка не создаёт дубликатов.
- [ ] Публикация открывается из внешней сети с действительным сертификатом только по HTTPS. Общие DNS и сертификат переиспользуются.
- [x] Проверки охватывают реальный loopback-сервис, повторное использование подключения, коллизию имени, недопустимые цели и попытки доступа другого владельца.


## Answer

Локальная реализация завершена. [Инструкция](../../../docs/publications.md).
Публикация проходит от отдельного HTTPS-хоста через статический Caddy,
Unix-сокет кабинета и агент к явно указанному приложению. В локальном
проверочном сценарии только WireGuard-сетевой seam заменён перенаправлением
на listener агента; настоящий WG/LXC или интернет не заявляются проверенными.
Проверены два разных приложения на одном подключении, в том числе HTTP API.

Поддомен закрепляется глобально SQLite-транзакцией. Создание повторного
идентичного запроса возвращает прежний ID; конкурентный выбор одного имени
между экземплярами кабинета даёт 201 и 409. Подмена machine ID / publication ID
другим владельцем отвергается. Агент получает карту зарегистрированных ID,
применяет монотонную версию и подтверждает applied_generation; до
подтверждения статус «Настраивается», после — «Настроена». Отказ новой карты
выводит причину ошибки новой публикации, сохраняя прежние применённые маршруты.
Повтор настройки использует ту же запись и поддомен.

После замечания пользователя о SOLID жизненный цикл выделен в
`internal/publication.Module`: авторизация и переходы состояния находятся
в модуле, SQLite-адаптер отвечает за атомарные снимки и транзакции,
forwarder — за допуск/отмену/учёт TCP-соединений; настоящий seam
`Transport.Endpoint` отделяет доставку через агент от ручного WireGuard.
HTTP-адаптеры не содержат SQL, транзакций или переходов жизненного цикла.
Машины и publication-модуль соединены через `agentcontrol.Controller` и
общий тип `agentprotocol.Acknowledgment`. Чистая проверка адреса находится
в agentprotocol, фактическая принадлежность IP проверяется внутри агента.

Первые тесты ожидания agent ACK падали до реализации, затем прошли.
При выделении модулей прежние HTTP-тесты сохранены без изменения сценариев.
Полный обычный набор cabinet/agent/command прошёл после слияния выделенного
machine-модуля. Публикационные сценарии прошли с race detector. `go vet`
для затронутых модулей и Linux amd64 сборки кабинета/агента прошли.
Настоящий локальный Caddy дополнительно проверен с wildcard-сертификатом
временного CA, которому доверяет только тестовый клиент. Проверен POST 9000 байт,
сохранение Host/path/query/Authorization и отсутствие утечки внутренних
заголовков, кабинетных CSRF/CSP/cookies в приложение.

`resolved` означает реализацию и локальные проверки по указанию пользователя
«Только локально». Критерии 1 и 9 остаются открыты: внешний DNS, публичный
сертификат, настоящие Debian LXC/WireGuard и вход из внешней сети требуют
отдельного стенда. Механизм bounded закрытия активных запросов подготовлен
в forwarder; интерфейс отключения и его приёмка относятся к задаче 05.
