# 03: Пользователь подключает Debian LXC через агент

**What to build:** пользователь добавляет свою машину в кабинете, получает одноразовый код и устанавливает агент внутри Debian LXC. Машина подключается к маме, а кабинет показывает состояние связи и время последнего контакта. Сценарий можно проверить на учётной записи из задачи 01 без ожидания приглашений.

**Blocked by:** 01 — Первый администратор входит в кабинет по HTTPS.

Status: resolved

- [x] Определены поддерживаемые версия Debian и конфигурация LXC, необходимые права агента и подготовка Proxmox-хоста. Пользователь получает исполнимую инструкцию; неподдерживаемое окружение не обозначается как успешно подключённое.
- [x] Пользователь создаёт запись своей машины и получает код подключения с определённым сроком действия. Код отличается от приглашения человека.
- [x] Агент устанавливается через терминал и подключает именно предназначенную ему машину. Просроченный или использованный код отвергается, включая конкурентное использование.
- [x] Определены протокол управления, хранение учётных данных и поведение незавершённого подключения. Секреты не выводятся в обычные журналы и состояние кабинета.
- [x] Агент работает фоновой службой и автоматически запускается после перезагрузки LXC.
- [x] В кабинете раздельно отображаются «На связи» / «Нет связи» и время последнего контакта; отсутствие связи не удаляет запись машины.
- [x] Машина связана со своим владельцем. Чужую машину нельзя прочитать или изменить подменой идентификатора.

## Answer

Реализация локальной части завершена: `internal/cabinet/machines.go`,
`machine_http.go`, `internal/agent`, `cmd/sreda-agent`, `deploy/agent`.
Инструкция: [Debian LXC](../../../docs/agent.md).
Срок кода — 15 минут; одноразовое потребление защищено SQLite IMMEDIATE
транзакцией и проверено между двумя экземплярами кабинета. Приватный
WireGuard-ключ остаётся на машине; сервер хранит хеш управляющей учётной
записи, отдельный секрет proxy защищён правами файла базы.

Проверки на согласованных CLI/HTTP seams с реальной SQLite: создание машины,
владелец и прямой доступ по чужому ID, конкурентное потребление кода,
отказ сети без потери кода, отсутствие секретов на странице, реальное
HTTPS-взаимодействие клиента агента с кабинетом и сохранение состояния 0600.
Агент proxy доставляет HTTP в зарегистрированный loopback endpoint,
отвергает произвольные назначения, отключённые и устаревшие карты маршрутов;
после потери связи принимает ту же актуальную карту, сохраняя монотонность.
Первые тесты падали до реализации; обнаруженные гонка двух SQLite-соединений
и потеря версии при приостановке исправлены red→green проверками.

В сетевой границе используется `tunnel.Gateway`: без настроенного helper
подключение закрыто. Сервис кабинета проверяет параметры WireGuard до
расходования кода, восстанавливает явно включённые peers после запуска
helper и раз в 30 секунд. После удаления записи адреса выбираются из первых
свободных 100, независимо от возрастающего ID машины.

`resolved` здесь означает завершённую реализацию и локальные проверки по
указанию пользователя «Только локально». Два последних сетевых критерия
приёмки не отмечены: Debian LXC, реальный handshake, изоляция kernel
WireGuard между двумя машинами и перезапуск LXC не выполнялись. Unit
автозапуска и исполнимый установщик поставлены, но реальный reboot остаётся
за стендом задачи 13. Политика helper реализована независимо от агента;
её применение на настоящей маме не заявляется проверенным.

Следующая задача 04 добавляет карты публикаций и подтверждение их версии.
Сейчас агент допускает literal loopback; расширить до literal IP, реально
назначенных интерфейсам этой машины, проверяя адрес внутри агента.
